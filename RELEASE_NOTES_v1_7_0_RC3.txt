LUXX v1.7.0 RC3 — ZERO-SURPRISE RELEASE
Launch date: Monday, September 7, 2026
Status: RELEASE CANDIDATE FOR INDEPENDENT REVIEW. NOT DEPLOYED.

RC3 is RC2A plus a full two-part zero-surprise audit: 21 defects found and fixed,
real-media acceptance closed against the creator's own 15:57 master, and a second
adversarial pass over the finished application. Everything below still applies.

This is a patch on the existing v1.7.0 CREATOR PILOT application. It was not
rebuilt. Primary navigation is unchanged and remains exactly three tabs:

    TODAY    LIBRARY    RESULTS

No fourth tab was added. No shoot engine, CRM, scheduler, messaging centre,
autonomous posting, multi-creator system or analytics platform was added.
Roles remain CREATOR and EXECUTIVE PRODUCER with identical powers; the role is
audit identity only.

Preserved unchanged: authorization/quarantine, immutable masters and derivative
lineage, tracking routes, locked baseline architecture, append-only action
history, frozen prescriptions, measurement corrections, persistence, optimistic
concurrency, operator attribution, the Netlify storage model and the same-site
deployment model.


================================================================================
1. CAM AVAILABILITY IS CONFIGURED, NEVER HARD-CODED
================================================================================

RC1 shipped a fixed cam window of 8:00-11:00 PM Central and fixed cam days, one
of which was Saturday. None of it was ever confirmed by the creator.

The constant is deleted. So is the LIVE entry in the frozen weekly schedule.

New in SETUP -> CAM AVAILABILITY (no new navigation):
  - allowed weekdays, chosen from Monday..Friday only
  - earliest available start time
  - latest available end time
  - creator timezone, defaulting to the existing America/Chicago setting

Saturday and Sunday are a hard constraint. They cannot be enabled from settings,
from an import, or from a schedule entry, and a weekend cam session cannot be
recorded.

Before availability is configured:
  - TODAY shows SETUP REQUIRED - CAM AVAILABILITY NOT FINALIZED
  - no LIVE job is scheduled and no clock time appears anywhere
  - the notice is deliberately NOT actionable

After it is configured:
  - LIVE appears only on the configured weekdays
  - the LIVE card carries the configured window and nothing else
  - the time remains GUESS / DEFAULT

Availability is a constraint. It is not evidence. No cam time is called optimal
until creator-specific measured results support that conclusion, and the cam
summary says so in plain words.

A cam session records: actual start, actual end, session minutes, creator effort
minutes, followers at start, followers at end, follower delta, tips/tokens,
native revenue, an optional theme, and notes. Cam remains native evidence only:
LUXX does not claim Chaturbate caused OnlyFans revenue.

Fixed while testing this: a datetime-local value has no timezone, and RC1 handed
that bare wall clock to Date.parse, which reads it as UTC. A real 9:05 AM Central
session resolved to 4:05 AM Central and was wrongly flagged as outside the
window. Zoneless timestamps are now resolved in the creator's timezone.


================================================================================
2. CAM IDEAS ARE OPTIONAL GUIDANCE
================================================================================

A LIVE job may carry one short optional theme: Bookish / Nerdy Daytime, Getting
Ready / Casual, Morning Coffee / Chat, or Behind-the-Scenes Shoot Planning.

They are GUESS / DEFAULT ideas. No theme is claimed to monetize better until
measured cam results support it. The theme actually used is recorded so early
sessions can be compared, and the guidance is to keep them comparable rather
than changing time, length, format and theme at once.

No cam-planning product was built.


================================================================================
3. PRODUCE IS OFF UNTIL A GAP IS DOCUMENTED
================================================================================

The creator is uploading a large existing library. LUXX does not know that she
needs new production, so it must not prescribe a shoot.

PRODUCE ships OFF. It never appears because the day has spare capacity, and
there is no PRODUCE entry anywhere in the weekly schedule.

A documented gap requires a typed category, an evidence reference from the
reviewed Library, and counted have vs counted needed. A claim that inventory is
short when the count says otherwise is rejected outright. Categories available
for future use: X face-safe teaser, Pornhub teaser derivative, PPV inventory,
paid-wall inventory, vertical acquisition, creative variety. None of them is
asserted.

If inventory is sufficient, NO NEW SHOOT NEEDED is the correct answer and LUXX
is able to give it. Existing authorized inventory comes first. No shoot engine
was built.

4. BASELINE IMPORT — ONE UPLOAD, THEN A HUMAN
================================================================================

New in SETUP -> IMPORT BASELINE (no new navigation). Structured JSON is
mandatory and supported; CSV is also accepted.

    {"rows":[{"platform":"X","metric":"followers","value":36,
              "unit":"count","evidence_reference":"x.png","notes":""}]}

    platform,metric,value,unit,evidence_reference,notes

Covers X, Pornhub, OnlyFans Free, OnlyFans Paid, ManyVids, Fansly, Chaturbate
and Linktree. Carries platform, metric, exact value, unit, evidence reference,
notes and explicit NOT AVAILABLE.

The required flow is enforced:

    IMPORT -> REVIEW -> CAPTURE BASELINE -> LOCK BASELINE

  - the import validates the file and populates the existing baseline review
    fields, preserving evidence references and notes
  - it does NOT capture and does NOT lock
  - it REFUSES to overwrite an already locked baseline, with a clear error
  - NOT_AVAILABLE, N/A and empty stay NOT AVAILABLE. They are never zero
  - a value that is neither a number nor a recognised unavailable token is
    rejected rather than guessed
  - the old August reference seeds on the account records are never read by the
    import, so they cannot be promoted into the September launch baseline

After lock the baseline is preserved historically and is never silently replaced
by later current values. Progress belongs in RESULTS and the action ledger.

5. WEEK-1 PPV BELONGS ON ONLYFANS PAID
================================================================================

RC1 defined the Wednesday, Saturday and Sunday PPV jobs against OnlyFans FREE.
All three now target OnlyFans PAID and resolve to OF_PAID_PPV_MESSAGE_01.
OnlyFans Free remains nurture and conversion toward Paid.

Supporting fix: candidates are now generated for every usable route on a
platform rather than only the single highest-priority one. A paid-feed wall post
and a PPV DM are different placements, therefore different routes, therefore
different jobs. Approving a job now honours the job's intent, so a PPV pick can
no longer be approved against the paid-feed route.


================================================================================
6. PPV EVIDENCE CONTRACT
================================================================================

The v1.6.1 treatment evidence contract is preserved and enforced. A locked-PPV
buyer pays on the PRE-PURCHASE TREATMENT, so evidence belongs to the treatment
class and never to the hidden master.

Treatment identity: preview style, delivery mode/route, audience segment, price
band, attribution scope. The treatment key contains no asset id, no filename and
no master identity.

CALL requires ALL of:
  - the same treatment class
  - the same attribution scope
  - a real denominator
  - at least the minimum qualifying sample (6) of comparable measured results
  - AND favourable evidence under the existing bounded/shrunk scorer

The minimum qualifying sample threshold PLUS favourable evidence. Reaching six
observations does not produce a CALL on its own. Six zero-unlock sends remain
GUESS. A PPV DM with no recorded sent_to remains GUESS, and LUXX never invents a
denominator at recommendation time.

Actual execution overrides the prescription. If the creator changes the preview,
the segment, the price or the delivery route, the result accrues to what was
actually used.


================================================================================
7. ASSET-EVIDENCE REGRESSIONS REMOVED
================================================================================

RC1 stamped asset-scoped language onto PPV lines: "measured results on this
asset", "measured results on this photo", "strongest option across N measured
results on this asset". That is the exact regression back to asset-based PPV
evidence.

Audited and corrected in the TODAY job card, selection state, READY TO APPROVE,
the frozen prescription, RESULTS, receipts, confidence copy and evidence
explanation copy. For PPV, GUESS and CALL now attach visually and semantically
to the pre-purchase treatment. Nothing calls a hidden master a proven, winning
or best-selling photo.

Asset-scoped wording survives only where the audience actually saw the file
before acting.


================================================================================
8. PORNHUB TEASER IS MECHANICALLY ENFORCED
================================================================================

A PH_TEASER job may select only a valid teaser or trailer derivative. A MAIN
CUT, a full scene, an original full video and a generic Pornhub-eligible video
are all refused, however eligible they are.

With no valid teaser derivative, TODAY shows HOLD / FIX LIBRARY and names the
reason. There is no silent fallback to a full video.

Existing historical Pornhub full videos are untouched. This restriction applies
to future prescriptions only.


================================================================================
9. LIBRARY TECHNICAL SCORE
================================================================================

LIBRARY still shows a visual technical score. It describes technical usability
only. It does not rank monetization, create CALL, imply conversion probability
or proven revenue, or produce a winning asset, and it does not influence TODAY's
monetization ranking: two identical candidates scoring 41 and 96 technically
produce the same candidate score. BEST VERSION means the best currently valid
derivative of that master, never best selling or best converting. No new
darkness, blur, exposure or beauty thresholds were invented.


================================================================================
10. TRACKING ARCHITECTURE AND HISTORICAL CONTENT
================================================================================

ONE SOURCE + ONE PLACEMENT + ONE DESTINATION = ONE ROUTE, unchanged. Bio, pinned,
post and message are never collapsed into one identity, and verifying one
placement never activates another. The Week-1 funnel remains X -> OF Free,
Pornhub -> OF Free, OF Free -> OF Paid, with Paid monetization measured natively.
No external route is activated until the exact live placement has been verified.

Existing Pornhub videos, ManyVids listings and OnlyFans history stay live and
stay historical truth. Structured historical intake is preserved with its full
field set and the KEEP / RE-EDIT / REPLACE / RETIRE review statuses. Nothing is
auto-retired on a technical score.

12. TODAY HOLD BEHAVIOUR
================================================================================

A job with no valid eligible content shows HOLD / FIX LIBRARY. LUXX does not
substitute another content type, unauthorized or quarantined media, a full
Pornhub scene in place of a teaser, or an unrelated asset to fill the schedule.
A missing valid candidate is a real state and is shown as one.

13. TEST SUITE REPAIRS
================================================================================

The browser suites were not green and were testing a LUXX that no longer existed.

  - browser-tests.py carried a hand-written Python re-implementation of the
    domain. It is deleted. /api/action now executes the REAL domain through
    tests/domain-bridge.mjs, so the UI is always exercised against current

    CHANGE / DECLINE -> APPROVE -> MARK POSTED.
  - Both used page.set_content(), which leaves the page on an opaque origin where

    now load from a real origin, and the app guards storage access anyway.
  - Removed stale selectors and labels: .media (now .mediaCard), EDIT / VERIFY
    (now SET UP / VERIFY), text inputs for what are actually select elements,
    UPLOAD + SAVE, BRAND SHOOTS.
  - Removed absolute machine paths: the suites no longer point at fixtures or a

    run time or supplied by environment variable, and the browser comes from
    Playwright.
  - browser-real-api.py now runs against the real Netlify functions through
    tests/local-server.mjs, which loads all 30 functions instead of 22.
  - Report assertions no longer pin exact counts copied out of an artifact, which
    is how a stale report survives a real regression.

No test report was edited to say PASS.

ADDENDUM — v1.7.0 RC2A: CREATOR CTA SELECTION FIX
================================================================================

Everything above still applies. RC2A changes one thing: how the creator picks a
ready-to-use caption. It is a UX fix. No evidence contract, scoring rule, tracking
route, baseline behaviour, cam availability rule, PRODUCE gate or navigation was
altered.

THE PROBLEM

READY TO APPROVE offered up to three captions, but only the first had a COPY
action. The alternates were plain text behind a disclosure, and using one meant
going through the generic CHANGE form and retyping it. In practice the alternates
were never used.

THE FIX

Every caption is now listed in the READY TO APPROVE card, each with its own:

    COPY            copies only that caption, with no need to select it first
    USE THIS CTA    switches the prescription to that exact caption

The selected caption is marked "SELECTED CTA" and offers no USE THIS CTA of its
own. Option 1 remains preselected. No new modal and no new screen was added.

HOW A SELECTION IS RECORDED

Selecting an alternate goes through the EXISTING prescription revision model:

  - the previous line becomes REVISED and keeps the caption it actually carried
  - a new PRESCRIBED line stores the exact chosen caption text, its index and
    cta_selection_source = CREATOR_SELECTED
  - the remaining options stay attached, so she can switch again
  - the revision reason is written for her: "Creator selected ready-to-use caption
    N of M"
  - re-selecting what is already selected is a no-op and creates no history
  - the chosen caption is frozen with the prescription on APPROVE, so the action
    ledger identifies which caption was actually selected

Nothing is overwritten. The revision chain is intact and auditable.

WHAT IS DELIBERATELY REFUSED

Only a caption already on that prescription can be selected. Free text is not
accepted here: an arbitrary caption is still a CHANGE with the creator's own
reason. Selecting a caption on a line that is not PRESCRIBED is refused.

WHAT WAS NOT ADDED

No CTA scoring, no winner labels, no copy ranking, no new evidence state, no CTA
analytics, no experiment engine, no navigation. A caption is not part of PPV
treatment identity and never will be from this change. Actual execution still
overrides the prescription, and no caption is claimed to perform better than
another.

TESTS

tests/cta-selection-test.mjs covers A..L: all options rendered, COPY on each,
USE THIS CTA on each alternate, the default preselected, selection updating the
visible state, the exact caption stored on the revision, repeated switching
preserving history, APPROVE still working and freezing the chosen caption,
CHANGE and DECLINE still working, the PPV treatment contract unchanged, GUESS and
CALL unchanged, and the surrounding release contract intact. Both browser suites
also drive the control end to end.

BUG FOUND WHILE TESTING THIS

The browser suites matched the job-card control by accessible name "USE THIS",
which Playwright matches as a substring, so the new "USE THIS CTA" button was
being clicked instead. Both suites now match that control exactly.
